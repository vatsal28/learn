Two things a day, from the workbench.

Two lessons from a day when reliable progress depended on careful recovery and honest execution signals.

System Design

Undoing Work Across System Boundaries

When one workflow changes several systems, compensating transactions provide explicit, tested actions that restore a safe business state.

What it is

A database transaction can roll back several writes inside one database. A distributed workflow cannot usually rewind every external system atomically. Instead, each completed step needs a matching compensating action that restores the intended business state. Compensation is not a blind technical reversal; it must understand what became visible, what remains

Yesterday’s example

Imagine a publishing service that promotes an article, refreshes a mirror, and archives its inputs. If the mirror step fails after promotion, the service can restore the previous article, leave the inputs untouched, and verify both readers

Why it matters

The concept arose because a multi-step release crossed several boundaries, and an unintended early action required a controlled recovery

Takeaway Design the undo path beside the happy path, and test recovery before automation reaches production.

Read the 2-minute version

The patternSaga patternA saga treats each committed step as reversible through a corresponding compensating action when later steps fail.

Good compensation starts with durable checkpoints. Record which step completed, the version it produced, and the safe state to restore. Make compensating commands idempotent so repeating recovery does not cause fresh damage. Use locks or version checks to stop concurrent work from overwriting the rollback. Some effects cannot truly be undone, such as an email already delivered, so order irreversible steps last whenever possible. After compensation, run outcome-based checks against every affected boundary instead of trusting a command's exit code. A saga may coordinate this centrally through an orchestrator or distribute responsibility among participating services. For small systems, a clear recovery ledger and a few explicit commands are often enough. The essential property is that partial success becomes a known, resumable state rather than an improvised emergency.

Agents & AI

Report Actions Only After They Exist

Agents should announce operational progress only after receiving concrete evidence that the underlying action actually started or completed.

What it is

Natural-language intent is not execution. An agent may plan to start a worker, run a command, or deploy a change, yet lose the turn before the action happens. An action receipt is concrete evidence such as a returned task identifier, process handle, created artifact, or verified endpoint. User-facing status should be derived

Why it matters

The concept arose when work was described as active before the execution layer had confirmed that any worker existed.

Takeaway Make narration lag execution by one verified event; never let confident language become the source of operational truth.

Read the 2-minute version

The patternAcknowledge after commitLike a consumer acknowledging work only after a durable commit, an agent reports state only after a verifiable tool result.

Action receipts turn vague agent progress into a small state machine. A request begins as pending, becomes started only when the tool returns evidence, and becomes completed only when the expected outcome passes a check. Failed or missing receipts remain explicit states rather than being smoothed over in conversation. Receipts should include the minimum useful correlation data, such as a job key, timestamp, expected artifact, and current status, while avoiding sensitive payloads. Long-running work also needs mechanical follow-up checks against the product itself, not merely the worker's heartbeat. This mirrors reliable messaging systems, where acknowledgment follows durable processing. It also improves recovery: after interruption, the next turn can inspect the receipt and decide whether to resume, retry, or report failure. The result is less theatrical progress and a much stronger boundary between reasoning, side effects, and truth.
