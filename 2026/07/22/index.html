System Design

Stop Configuration Drift at the Source

Duplicate operational rules quietly diverge; one canonical contract keeps every runner aligned.

What it is

Configuration drift appears when scheduled, manual, and recovery paths copy the same behavior. Small local fixes make those copies diverge until identical inputs produce different outcomes through different entry points.

Yesterday’s example

Imagine a batch service whose timer retries failed work, while its command-line runner skips retries and its recovery job checks an outdated output location. Each path seems valid alone.

Why it matters

Hidden divergence makes operations unpredictable. Tests often exercise only one route, successful exits stop proving that expected artifacts exist, and incident diagnosis becomes a hunt for whichever procedural copy actually ran.

Takeaway Centralize behavioral rules, keep entry points thin, and verify artifacts from every path.

Read the 2-minute version

The patternSingle source of truthOne authoritative workflow contract supplies the same behavior to scheduled, manual, and recovery entry points.

Drift usually begins with sensible edits: one runner gains a retry, another receives a newer path, and a recovery route retains an older gate. The danger appears only when they stop representing one system. A stronger design separates concerns by rate of change. Put ordering, validation, retries, and completion checks in one executable contract. Keep domain policy separate when different owners change it independently. Entry points become adapters that choose timing or mode and pass bounded inputs. During consolidation, inventory obscure recovery behavior, run representative fixtures through every route, and compare final artifacts. Future behavioral changes then update the canonical contract first, turning hidden divergence into a visible review decision.

Agents & AI

Let Agents Abstain on Risky Classification

A useful agent needs an explicit abstain path when uncertain classification could hide important work.

What it is

Selective classification adds an abstain outcome to automated decisions. The agent handles confident, low-risk cases, while mixed, sensitive, or uncertain items remain unchanged for a person to review safely.

Yesterday’s example

Consider a generic inbox assistant that moves obvious bulk promotions but leaves conversations mentioning payments, deadlines, security, or personal replies untouched. Ambiguous threads stay visible instead of receiving a forced label.

Why it matters

False positives and false negatives carry different costs. One unnecessary review creates friction; hiding an urgent message can cause damage. The automation threshold should reflect that imbalance, not maximize activity.

Takeaway Automate obvious low-risk cases and route uncertainty to a reversible human review path.

Read the 2-minute version

The patternHuman-in-the-loopThe agent handles confident routine cases while ambiguous or costly decisions remain available for human review.

Complete classification assumes every input deserves an action, but that fails when mistakes have unequal consequences. Start by comparing the harm of unnecessary review with the harm of an incorrect mutation. Protect categories where the second cost dominates and make uncertainty fail safe. Evaluate the full unit being changed, because a harmless message can share a thread with a sensitive reply. Keep execution reversible, attach reason codes, and record enough information to undo batches. Measure precision on automated actions, abstention rate, review burden, and costly escapes. A rising abstention rate can reveal changing inputs or weak instructions; a low rate is not automatically better. The aim is dependable workload reduction within a risk budget, not maximum autonomy.
