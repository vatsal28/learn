Two useful ideas from yesterday’s work.

System Design

Fault isolation

Separate failure domains so one broken stage does not misdiagnose or destroy valid work.

What it is

Fault isolation divides a workflow into stages with distinct responsibilities, durable handoffs, and precise error categories. Each stage preserves successful upstream output and reports its own failure.

Yesterday’s example

A publishing flow once treated a missing build dependency as defective writing. The safer version keeps the approved draft, checks prerequisites near the renderer, restores locked packages, and identifies the broken stage.

Why it matters

The diagnosis now points recovery toward infrastructure without discarding creative work. A later retry can resume from the saved handoff instead of repeating every successful step.

Takeaway Preserve completed work and name the failing layer before attempting recovery.

Read the 2-minute version

The patternBulkhead patternStage boundaries contain infrastructure failures so valid upstream artifacts remain intact.

Begin by deciding which components can fail independently and what durable evidence each must leave. Imagine a report generator with drafting, checking, rendering, and delivery. A renderer that cannot locate a font package has learned nothing about the report’s accuracy. It should emit a rendering-specific failure while leaving the approved input untouched. Place prerequisite checks beside the component that owns them. A renderer verifies binaries and locked packages; a delivery service verifies credentials and connectivity. Neither edits source material to compensate for its own problem. Useful error categories make the boundary operational. Distinguish invalid input, absent dependency, unsuccessful build, and rejected delivery. Each category maps to a narrow response: revise input, restore packages, rerun rendering, or pause sending. This reduces diagnosis time and makes retries safe because the system can restart at the failed boundary rather than replaying completed work.

Agents & AI

Planner–executor–critic

Split complex agent work into planning, execution, and independent review with explicit handoffs.

What it is

This pattern assigns specification, implementation, and verification to distinct roles. A planner defines constraints, an executor performs bounded work, and a critic tests artifacts against acceptance criteria.

Yesterday’s example

For a complex setup, the plan first named allowed surfaces and checks. An implementation agent followed that brief, while a separate review inspected files, test output, and a generated artifact.

Why it matters

The executor could no longer make the final success judgment alone. Explicit handoffs exposed assumptions, and review converted completion from a confident statement into a testable claim.

Takeaway Make completion a reviewed claim supported by artifacts, not an executor’s self-assessment.

Read the 2-minute version

The patternGenerator–critic patternOne role produces a candidate result while another evaluates it against explicit acceptance criteria.

The planner turns an ambiguous request into scope, constraints, risks, and observable checks. The executor receives that bounded brief and produces artifacts. The critic examines those artifacts instead of accepting the executor’s narrative. These roles need separate contexts, though they do not require different models. A strong handoff names permitted surfaces, forbidden actions, expected outputs, and verification commands. An agent editing a site, for example, may change templates and assets while deployment remains prohibited. Review can then inspect the changes, run a build, and compare the rendered result with the original brief. Artifact-based milestones also improve supervision during long runs. A saved model, passing test, generated sample, or scoped commit is stronger evidence than an “active” status. The extra coordination has a cost, so use this structure for risky, multi-step, or externally visible work. For small reversible tasks, a single agent with a concise checklist is often enough.
